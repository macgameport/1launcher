## 2. Target

Apple's file-system guidance gives each kind of file a place under `~/Library` and tells apps to keep the files they create themselves there, by convention in a subfolder named for the app's bundle identifier. This project is several apps, so it uses its own name, as Porting Kit does on this Mac.

By that guidance: the apps stay in `~/Applications` and the launcher logs in `~/Library/Logs/`. Files an app keeps for itself go under `~/Library/Application Support/<name>/`: **the runtime folder**, what a game runs and a game's own state. `~/Library/Caches/<name>/` is for things an app can make again, and holds nothing of ours: section 1 shows the workspace is not that. `~/Library/Developer/` is, in Apple's table, "data used by Xcode and other developer tools": **the workspace** (O3).

```
~/Library/Application Support/1launcher/      the data root (exists: Surviving Mars uses it)
├── cities-skylines-2/                         the runtime folder: the launcher, repatch.sh, the display-profile
│                                              helper, patches/, and the badge script where opted in
└── surviving-mars-relaunched/                 backup/, runs/, and the launcher's copy and tools/ its app runs
~/Library/Developer/1launcher/                 the work root (exists): durable, and no space in its path
├── cities-skylines-2/                         the workspace: everything else in today's ~/cs2-patch, names unchanged
└── surviving-mars-relaunched/                 engine/ and the probes' folders
```

**Two rules map every old path.**

1. **The runtime names** become `<data root>/cities-skylines-2/<name>`: `launch-cs2-dxmt11.sh`, `repatch.sh`, `cs2-display-profile.sh`, `patch-modconflict-badge.py`, `patches/` (as one folder, with its markers, `_vendor` and anything else in it), and three kinds that only an older setup left: `launch-cs2.sh`, any `launch-cs2*.sh.bak`, and `revenv/`.
2. **Every other** `~/cs2-patch/X` becomes `<work root>/cities-skylines-2/X`.

Nothing is renamed, regrouped or deleted, and the four trees stay beside each other. The three old kinds travel with the runtime, though nothing uses two of them, for two reasons. A player's install holds runtime names and nothing else; if `revenv/` or an old launcher counted as "everything else", that one leftover would make a workspace under `~/Library/Developer` on a Mac that has no use for one (pass 2's D8, which found the same for the launcher backup). And deleting someone's files is not the move's to do: where `launch-cs2.sh` or `revenv/` is present, setup's closing lines name it as no longer used and safe to delete (3.3), and on the Studio both are on L2 step 0's list. On the Studio the home folder ends with no `~/cs2-patch`.

Why two places. The runtime folder is what the standard's Application Support is for, and P1 shows an app can run scripts there. The workspace is not an app's support files: it is 62 G of evidence, experiment output and live source, written by the harness scripts under `scripts/`, which were never made safe for a path with a space, and it includes Wine trees. It needs a durable folder with no space in its path; O3 says where.

Unchanged: the wrappers, one wrapper per game, the log paths, CS2's deploy model (copies outside the repo, because an app may not run scripts from a clone under `~/Documents`: `scripts/setup.sh:20-21`), and everything of Surviving Mars's, which already uses both roots.

**3.3 An install made before this keeps working where it is, as one folder, until setup moves it.**

*The rule (`common/paths.sh`).* If `<data root>/cities-skylines-2` does not exist, and `~/cs2-patch` is a real folder (not a symlink), and both roots are at their defaults, then `CS2_DATA` and `CS2_WORK` are both `~/cs2-patch`. Otherwise they are the two new folders. One observable decides both, so an old install is never half-moved by a default; a root counts as set only when it differs from its default, so sourcing the file twice, or inheriting its values, changes nothing.

*A folder is "named"* when `--dest` is given, or `CS2_PATCH_DIR` is set, not empty and not the default runtime folder, or either root is set away from its default (`L1_ROOTS_SET` is 1). Setup then installs where it was told, as it does today, and never calls the move: a named folder is not moved, and nothing is moved into a root someone set (so a test or a trial with scratch roots cannot reach the real `~/cs2-patch`).

*What setup prints and does.* Under its `repo:` line (`scripts/setup.sh:89-90`) setup prints `data:` and `work:` lines, through `tilde()` (`:72`), and then a `move:` line; none of the three with `--mac-only`. The `move:` line needs the wrapper, for its lock (3.4), and the header comes before the preflight has found one (`:126-137`). So the wrapper is found once, above the header, by a function that holds the test of `:128-135` and keeps today's behaviour: if `CS2_WRAPPER` is set, that wrapper when it has a prefix and none otherwise; if it is not set, the first name in `WRAPPERS` (`:63`) that has one. The preflight's block reads that answer, and with no wrapper the move script is given no `--lock`. (P7 built this as a helper that repeats the loop; the build makes it the one function.) `--check` prints the three lines and stops where it stops today (`:166`), having moved and created nothing; its `move:` line comes from `scripts/move-install.sh --dry-run`, and its exit code is today's, 0 when the preflight passes, whatever the dry run reported, a stop included (measured, P7); the one exception is the "already moved" stop, after the table. A full run calls the move script after the preflight and the caution question (`:167`) and before the first copy (`:172`); the move script, not setup, decides whether there is anything to move, so the same call finishes a part-way move. Setup reads three things from the script: the `state:` line that opens its output (3.4), its exit code, and whether a `moved:` line is present. It drops line 1 (`state:`) and the script's closing "run setup" line, and relays the rest; `state: none` prints line 1 only, so nothing is relayed then.

| State, nothing named | `state:` | The `move:` line | A full run |
|---|---|---|---|
| no `~/cs2-patch`, no runtime folder | `none` | `a new install` | installs into the runtime folder. A workspace that is already there is left as it is |
| no `~/cs2-patch`, the runtime folder present | `none` | none | as today, in the runtime folder |
| no `~/cs2-patch`, and the workspace holds a runtime name that the runtime folder lacks (the runtime folder present or not) | `part-way` | `an earlier move stopped part-way; this run finishes it`, with the dry run's moves; or `an earlier move stopped part-way and cannot be finished now`, with the reasons | the move script finishes it (3.4). The owner does nothing but run setup |
| `~/cs2-patch` a real folder, no runtime folder | `old` | `will be moved`, with the dry run's moves; or `cannot be moved now`, with the reasons | by the move script's exit code (3.4) |
| `~/cs2-patch` a symlink, no runtime folder | `old` | `cannot be moved now`, with the reason (`~/cs2-patch is a symlink`) and a line saying that setup will install into the runtime folder and leave the link and what it names alone | the move is skipped. `common/paths.sh` does not take a symlink for an old install, so setup makes a new install in the runtime folder, beside the link, and its closing text says that. From the next run this Mac is in the "both" row |
| both: `~/cs2-patch`, real or a symlink, and the runtime folder | `old` | a `WARNING` that both exist, naming the folder the app's shim starts now | the move is skipped (the game-folder reason); setup goes on in the runtime folder, which is what `common/paths.sh` resolves, so after the run the shim starts the runtime folder. The warning says to remove `~/cs2-patch` only when it holds nothing but deployed copies |
| a folder named | not asked | `stays where it is: a folder was named` (when `~/cs2-patch` exists) | as today, in the named folder |

After the move script's exit 0, setup sources `common/paths.sh` again, takes its folder from it and, when something moved, prints the `data:` and `work:` lines again. After a skip it goes on in the folder `common/paths.sh` resolves: `~/cs2-patch` where that is a real folder and there is no runtime folder, and the runtime folder in the "both" row and the symlink row. A finishing run can be skipped only for a root that is not the user's own, on which setup's own check below stops too, or for a set root, with which setup does not call the script; so setup never copies into a half-made runtime folder after a skip. If `CS2_PATCH_DIR` names `~/cs2-patch`, that folder is absent and the runtime folder exists, setup stops with exit 1 and says the install has already moved. That stop sits in the header, where the `move:` line is made, so it fires under `--check` too: it is the exception to "`--check` exits 0 when the preflight passes" (LT17). With nothing to move, setup's output differs from today's by the header lines and the folder it names and by nothing else (LT17).

*The new folder is the user's own.* Setup adopts `own_folder` from Surviving Mars's setup (`surviving-mars-relaunched/scripts/setup.sh:112-117`): where setup's folder is under the data root, then the data root, the runtime folder and its `patches/`, each if it exists, must be a real folder of this user's that group and others cannot write to, or setup stops with exit 1 and that script's words; a folder setup or the move script makes is made with `mkdir -p` and `chmod go-w` (`:135` there). A named folder, and an old folder a skip leaves in use, are treated as today. The check sits after the move and before the first copy (P7 built it there), so `--check`, which stops earlier, does not report it; on an old install the dry run reports a root that fails it as a skip reason.

*Three voices.* Setup already speaks differently by route (`scripts/setup.sh:229-235`, `:255-261`, `:324-327`). The move's words follow the same test:

| Voice | When | "Run again" | The line that declines |
|---|---|---|---|
| a fetched copy | `L1_FETCHED_REF` is set | open the installer again | "put `CS2_PATCH_DIR=~/cs2-patch` and a space in front of the line you pasted", and the guide's address (`GUIDE`, `:85-86`), where the whole line is |
| the installer run from a clone | `CS2_VIA_INSTALLER=1` and no `L1_FETCHED_REF` | open the installer again | `CS2_PATCH_DIR=~/cs2-patch bash scripts/install.sh` |
| a checkout | neither | run setup again | `CS2_PATCH_DIR=~/cs2-patch bash scripts/setup.sh` |

`CS2_PATCH_DIR=~/cs2-patch` is one literal in setup, `~` included, and every form is built from it (LT20a). The variable reaches setup on every route: nothing between the pasted line and setup unsets it (the root `install.sh:123`; `scripts/install.sh:121`; `common/install-core.sh:271` unsets `WINEPREFIX` and `LOCK` only), and the shell turns the `~` into the home folder before the installer starts (P6). Declining is per run: someone with no checkout puts it in front of the pasted line every time, a game update's run included; exported in the shell profile, it stands.

The move script's lines are printed when the move is made, under a heading of setup's. After a move, setup's closing text says what went where; that anything of the owner's that names `~/cs2-patch` (a copied `.command`, an alias, a second app made with `make-shortcut.sh --name`) must be pointed at the runtime folder; which of `launch-cs2.sh` and `revenv/` came along and can be deleted; and, in its voice, the line that declines, with the guide's section for putting a folder back. After a skip it says why, that the install keeps working where it is (in the symlink row: that a new install was made beside the link), and that the next run tries again. Both blocks are printed at every end a run reaches after its first copy: the complete end and the exit-5 end (after `:350`), and before the exit 1 of a run that ends with problems (`:328-331`), since a run that moved the folder and then met a failed patch pass must still say where the folder went. (P7's build printed them after `:350` only.)

**3.4 The move is a script, not typed commands.** `scripts/move-install.sh [--dry-run] [--lock <path> [--held-by <pid>]]` does for anyone what L2 does on the Studio. It takes its targets from `$L1_DATA_ROOT` and `$L1_WORK_ROOT`, never from `CS2_DATA`, which names the old folder until it has run. Its output is an interface: setup relays it and reads it, and three different outcomes exit 0. Line 1 is `state: none`, `state: old` (a `~/cs2-patch` is there, real or a symlink) or `state: part-way`. Then come lines indented by two spaces: one per reason (`stop: …` or `skip: …`), one per move (`would move: A -> B` in a dry run, `moved: A -> B` in a real one), and `left in the workspace: <name>` for a runtime name both folders hold. Then unindented closing lines: `Nothing was moved.`, the command that finishes a part-way move, or the line that says to run setup. Setup drops line 1 (`state:`) and the closing "run setup" line, and relays the rest; `state: none` prints line 1 only. Every path in it is printed with the home folder as `~`, as setup's are, so that no relayed line carries the user's name. (P7's build told the exit-0 outcomes apart by matching its own prose; the `state:` line replaces that.)

*Part-way* is: no `~/cs2-patch`, not even a symlink; the workspace a real folder; and in it a runtime name that the runtime folder lacks (P7 built this definition). With `state: none` the script exits 0 at once and probes nothing. Otherwise it looks, moving nothing, for two kinds of reason not to move:

| Kind | Reason | How it is found |
|---|---|---|
| **Stop** | a script is running from the top of the old folder, a launcher or a `repatch.sh` run by hand: going on would copy over a script that bash is still reading (`scripts/setup.sh:177-178` write in place) | `lsof -t --` on the regular files that match `*.sh` at the top of the old folder prints a process (P6). With no such file `lsof` is not called: an unmatched pattern must not reach it as a name. Given several files, `lsof` exits 1 when any of them is not open, so its output is read and not its exit code (measured at pass 7's fold). The reason names the process found. The Studio's `launch-cs2-dxmt11-windowed.sh`, which is no runtime name, and the workspace's own scripts are covered too; that costs a wait and nothing else |
| **Stop** | another launch or install is using this game's wrapper | the launch lock at `--lock` names a live process other than `--held-by`. Setup passes its wrapper's lock (`<wrapper>/Contents/SharedSupport/prefix/.launcher.lock`), and `--held-by "$PPID"` only when `CS2_VIA_INSTALLER=1`: the installer takes that lock before it runs setup and frees it only at its own exit (`scripts/install.sh:106`, `:121`; `common/install-core.sh:360-365`, `:70`), and setup is its direct child. This is Surviving Mars's rule (`surviving-mars-relaunched/scripts/setup.sh:100-107`). Run by hand with no `--lock`, the script reads the lock of the wrapper setup would choose (`scripts/setup.sh:128-135`): if `CS2_WRAPPER` is set, that wrapper when it has a prefix and none otherwise; if it is not set, the first name in setup's list (`scripts/setup.sh:63`) that has one; with none, there is no lock reason. (P7's build read the first name on the list whether or not it was there) |
| Skip | one of the user's processes has its working directory inside the old folder (the system does not refuse such a rename: the process is carried along under a path that no longer exists) | `lsof -a -d cwd -u <uid>` |
| Skip | a game folder is already there: `<data root>/cities-skylines-2` or `<work root>/cities-skylines-2`. The roots themselves are expected to exist: Surviving Mars made both. Not a reason for a finishing run, which finds the workspace, and the runtime folder present or not (after `L1_MOVE_STOP_AFTER=rename` there is none) | `-e` or `-L`, so a dangling symlink counts |
| Skip | a symlink where a real folder is needed: the old folder, either root, or a runtime name at the top of the old folder | `-L` |
| Skip | a root that exists is not the user's own (`own_folder`, 3.3) | `stat` |
| Skip | the old folder and the nearest existing parent of each target are not on one volume | `stat -f %d` |
| Skip | the checkout the script runs from is inside the old folder | resolved paths |
| Skip | a root is set away from its default (a run by hand; setup does not call the script then) | the comparison of 3.3 |

It does not look for `wineserver`, and it reads no other game's lock: another game's Wine and the storefront's Steam leave setup working as it does today. This game's launcher takes its lock at `launchers/launch-cs2-dxmt11.sh:218` and frees it by the `trap … EXIT` of `:219`, so it holds the lock, and bash holds the launcher's file open, until the launcher itself ends, after its Steam shutdown (`:404` is only where the game starts). The two stops cover a running game.

Then it moves. It makes a missing root with `mkdir -p` and `chmod go-w`. If the old folder holds nothing but runtime names, `.DS_Store` aside, it renames the old folder itself to the runtime folder: one rename, and no workspace. Otherwise it renames the whole folder to the workspace first and lifts the runtime names out of it into the runtime folder. If the first rename itself fails, nothing has moved: it says so as a skip and exits 1 (P7). A run that stops after it prints the command that finishes it, and a second run finishes it. A finishing run looks for three things only: the launch lock (a stop), `own_folder` on the data root and on the runtime folder where they exist, and a set root. It lifts each runtime name the runtime folder lacks. A name both folders hold stays in the workspace and is named once, by that run's `left in the workspace` line; the runtime folder's copy is never written over (no `mv -f`), and such a name does not make the state part-way, so the next run reads `state: none` and says no more of it. Between the rename and the lift `CS2_DATA` names a folder that is not there yet. Only the move script runs in that window, it does not read `CS2_DATA`, and its exit 2 makes setup stop before it copies anything, so nothing is built in a half-made runtime folder. Last, after a move or a finish, it runs `chmod -R go-w` on the runtime folder (macOS's `chmod -R` follows no symlink): setup then copies in place, and `cp` over a file that exists keeps that file's mode, so a launcher that was writable by others in a mode-777 old folder would stay so. Surviving Mars's `put()` sets 755 for the same reason (`surviving-mars-relaunched/scripts/setup.sh:137-139`). P7's build ran `chmod go-w` on the two folders only; the files are owed. It changes nothing else: every marker in `patches/` moves with that folder, so a badge choice survives.

| The move script's exit | Meaning | Setup | The installer (it exits with setup's code, `scripts/install.sh:121-122`) |
|---|---|---|---|
| 0 | moved, finished an earlier move, or nothing to move | goes on in the folder `common/paths.sh` now resolves | as setup ends: 0, 1 or 5 |
| 1 | skipped: nothing moved, every reason printed (a first rename that failed is one) | prints the reasons and goes on (3.3); its own exit is as it is today | the same |
| 2 | stopped part-way | stops before copying, with the script's message, and exits 1 | 1, "The install stopped. The lines above say why." (`common/install-core.sh:79`) |
| 3 | stop: nothing moved | stops before copying and exits 3, a code new to this setup and the one Surviving Mars's setup uses for "a launch or an install is using the wrapper" | 3, which its own header already gives as "the game, another install, or another wrapper's Steam is running" (`scripts/install.sh:14-15`) |

`--dry-run` prints the reasons and the moves and exits as the real run would have: 0, 1 or 3. The script reads two variables that exist for its tests, as `common/install-core.sh:40` reads `L1_KILL`: `L1_MOVE_PROBE=<program>` replaces the two `lsof` calls and the volume read (`<program> open <files…>`, `<program> cwd <folder>`, and `<program> dev <folder>`, which P7 did not build and LT16's volume case needs), and `L1_MOVE_STOP_AFTER=rename` stops it after the first rename. Run on its own, its last line says to run setup (`state: none` aside, which prints line 1 only). The installer's check of its own files (`scripts/install.sh:115`) gains `common/paths.sh` and `scripts/move-install.sh`, so a temporary copy that macOS has thinned ends in the installer's exit 4 and not in setup's exit 1. `INSTALL.md` gains a short section, "If your install was made before the folders moved": what setup does to such an install; what stops working until it is pointed at the runtime folder; the line that declines, in the pasted form and the checkout form, and that it is per run; the moves that put a folder back (one `mv` for an install with no workspace; else the workspace back to `~/cs2-patch`, the runtime names back into it, and the emptied runtime folder removed); and what to run after them: the line that declines, on every run, or `v0.1.0` for the old code as well (3.7).

*The changelog and the release commands* are as the fifth pass left them. A root `CHANGELOG.md` holds one section per release, `## v<number> (<date>)`, newest first, under a `## Unreleased` section. No other line in a section starts with `## `, and the date is the day the heading's commit was made. A release is an annotated tag and a GitHub release whose text is that tag's section, copied by a command and never typed into the page:

```bash
sec() { git show "${2:-$1}:CHANGELOG.md" | awk -v v="$1" '{ sub(/\r$/, "") } index($0, "## " v " ") == 1 || $0 == "## " v { p = 1; next } /^## / { p = 0 } p'; }
sec v0.1.0 <commit> | grep -c '[^[:space:]]'     # 0 means a mistyped heading: stop
git tag -a v0.1.0 -m v0.1.0 <commit> && git push origin v0.1.0
sec v0.1.0 | gh release create v0.1.0 --verify-tag --title v0.1.0 --notes-file -
```

`sec <tag>` reads the tag's own copy of the file; `sec <name> <commit>` reads another commit's. Before the commands, in the checkout the tag is cut from: the commit is pushed and is on `origin/main`, and the unification plan's identity gate (its T5) names the project identity, because a tagger and a release author are public and permanent.

## 7. Not in this plan

- **Moving the wrappers.** `~/Applications` is the standard place.
- **Regrouping what is inside the workspace**, the log paths, and making the harness scripts safe for a space.
- **A second disk.** O7's mirrors cover the two repos that have commits of their own, and sit on the same disk as the originals. Still in one copy only: `dxmt-fork`'s 3 modified files, the two changed Wine source files and `ntdll-variants/` in `build-1116-unify`, and the 4 extra entries in the repo with no commit.
- **Rebuilding an engine** from a moved tree, and proving a Wine build at a path with a space.
- **Following a symlinked `~/cs2-patch`.** The rule of 3.3 does not take it for an old install and the move skips it, so setup makes a new install in the runtime folder beside the link and says so (3.3's row, LT17, LT18); what the link names is left to its owner. The two others the fourth pass met are fixed (`scripts/setup.sh:37-39`, `:269`).
- **Writing the launcher beside the old copy and renaming it**, as Surviving Mars's setup does (`surviving-mars-relaunched/scripts/setup.sh:137-141`). Setup still copies over the launcher in place, with or without a move; 3.4's stop covers only a run that would move. It wants an issue.
- **A launcher warning when `CS2_PATCH_DIR` points away from its own folder.** The variable is honoured today and still is.
- **A way to decline from the installer app.** None has been released. An environment variable cannot be put in front of a double-click, so an app, if one is released, declines by the pasted line.
- **Protecting `main` and `release`, signing tags, and releases cut by automation.** GitHub's setting that makes a published release immutable belongs with it: 3.7's rule is kept by hand until then.
- **A rule for later releases.** This plan cuts two. When a third is due, and whether a patch re-derived for a game update gets one, is not decided here.
- **A version line in setup's output.** A fetched copy already prints its commit (the root `install.sh:121`).
