# Claude Instructions — macOS game ports, one folder per game

One repository, one folder per game. A game may keep its own `CLAUDE.md` (Cities: Skylines II does,
Surviving Mars does not yet); the rules in this file hold for all of them. Personal-tier project: **no phases, no SPEC.md**; GitHub Issues are enabled and used
for umbrella work.

**Published addresses.** Every pasted installer line and every installer app that has been published fetches
`https://raw.githubusercontent.com/macgameport/1launcher/release/install.sh` and hands it a game's Steam app
ID; that script fetches this repository, finds the ID's row in `common/games.tsv`, and runs
`<that row's folder>/scripts/install.sh`. **A published thing names a game by its Steam app ID and never by
its folder**, so a game's folder may be renamed by changing its row. So: the root `install.sh` and
`common/games.tsv` are never moved, and a row's first field never changes; the names
`macgameport` and `1launcher` are never renamed or given up (a freed name can be claimed by anyone, and every
published installer would fetch from it); the branch `release` only ever moves forward, by a deliberate
`git push origin <commit>:release` after the test suites pass on that commit and on James's word, never by
force and never by the automatic push to `main`; and installer apps are released as `installer-<n>`, created
with `--latest=false`, a tag that is never moved. With the built-in update (`docs/plans/built-in-update.md`, 3.7), from the release that carries it: the root `CHANGELOG.md` is never moved, and the form of its version headings is read by every installed Mac; `install.sh update` is a published word that can never be withdrawn; so, from the release whose `release` holds it, is `install.sh launcher` (`docs/plans/launcher-first-install.md`, section 9), with the form `launcher <ref>`, and with it `common/install-launcher.sh` becomes a contract between versions: its path, its call with no argument and the meaning of its exit codes never change. **A row of `common/games.tsv` is shown:** from that release every row on `release` is a tile in every 14unch3r built from it, so no row reaches `release` before the game's installer works there, and no row is ever removed; `release` moves only to a commit a `v` tag names (`common/check-release-move.sh` asks it); and no tag is ever named `release`. **Published since 2026-11-16:** `release` first made at `e4aa901`, with the pasted line only (ND1);

**Two rulesets on GitHub hold this since 2026-11-25** (`docs/plans/built-in-update.md`, "UD5's rulesets"): `release` cannot be force-pushed or deleted, and a pushed `v*` or `installer-*` tag can be neither moved nor deleted, by anyone, while they stand. A mistyped tag stays, so the checks under "Releases" come before the push of a tag.
`release` and the `v` tags are different names: `release` is what the pasted line installs and moves forward;
a `v` tag is a fixed name for one version, which anyone can ask for, and is never moved.

**Releases** (`docs/plans/local-files-layout.md` 3.7, decided 2026-11-09, O10). A release is an annotated tag
`v<a>.<b>.<c>` and a GitHub release whose text is that tag's section of the root `CHANGELOG.md`, copied by a
command and never typed into the page. The second number rises when a change asks someone with an install to
do or notice something, the third for fixes, and the first stays 0 until James calls a release 1.0; one number
covers the whole repo. `CHANGELOG.md` has one section per release, `## v<number> (<date>)`, newest first, under
`## Unreleased`; no other line in a section starts with `## `, and a link in a section is a full `https://`
address that names the tag. A section is read inside 14unch3r before a player says yes to an update. Each change opens with one bold sentence saying what a player will notice or must do; pointers to plans and to code come after it. A published tag is never moved or deleted: a wrong release gets a successor, its
section gains a first line on `main` naming it, and its page is made equal with
`sec <tag> main | gh release edit <tag> --notes-file -` (asked of James first). Before the commands: the commit
is pushed and on `origin/main`, and the project identity is checked (`gh auth status` shows `iosoceans`):

```bash
sec() { git show "${2:-$1}:CHANGELOG.md" | awk -v v="$1" '{ sub(/\r$/, "") } index($0, "## " v " ") == 1 || $0 == "## " v { p = 1; next } /^## / { p = 0 } p'; }
sec v0.1.0 <commit> | grep -c '[^[:space:]]'     # 0 means a mistyped heading: stop
git show <commit>:CHANGELOG.md > /tmp/changelog-to-tag.md && bash common/updates.sh --version-of /tmp/changelog-to-tag.md   # must print v0.1.0: installed Macs read this heading
git tag -a v0.1.0 -m v0.1.0 <commit> && git push origin v0.1.0
sec v0.1.0 | gh release create v0.1.0 --verify-tag --title v0.1.0 --notes-file -
```

**Branches: only when required** (James, 2026-11-26: "branch only when required, at least until someone else joins the project"). Work is committed to `main`. A branch is cut only when something needs one: a second session working at the same time in its own git worktree, since git checks out a branch in one worktree only. `main` is not what players install (`release` is, and it moves only to a `v` tag), so unreleased work is safe there, and a live step installs from it with the root `install.sh`'s ref (`main`). ## Model tier — this repo is where the rule was earned

> The rule is now global (`.claude/rules/engineering.md` § *Escalate the model tier by SURFACE, not
> by task*), promoted 2026-09-03 after cs2 → homeOne → isnotus. The condensed evidence lives there.

**Instance 1 (2026-09-03).** Execution found the behavioural defects at any tier — three hunks
carrying vendor context rather than the predicted two, `assert()` baking `__LINE__` into the object
so a comment-only edit is not byte-identical, a probe leaking a running churn on its abort path,
the exact anchor a relocated hunk needs. Every one surfaced from a build, a mutant or a
byte-compare. **The gate was the reviewer.** The top tier found what no gate can reach: a plan
asserting a 131-entry unixlib table that is really 132 — its own test gate would have failed red
for the wrong reason; an install step whose `codesign` contradicted the same plan's `cmp` outcome
test; a test stating a pass condition absent from the tool's vocabulary; cites off by one after a

[#6](https://github.com/macgameport/1launcher/issues/6) — comment accuracy in the
published winemac reference, where `strip-comments.py`, the object comparison and the whole C29
